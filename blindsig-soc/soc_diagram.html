BlindSig SoC — The Full Story

SoC scaffold complete — ready for production crypto core drop-in

Part 1 — The Accelerator (Current: Toy Implementation)
Currently a placeholder that computes operand² mod modulus in 4 clock cycles. This is a stand-in for the real crypto core — it proves the register interface, bus integration, and firmware driver all work. The production module (Montgomery multiplier, modular exponentiation) drops into the same register interface without changing any surrounding infrastructure.
What Changes for Production — What Stays the Same
The current accelerator is a toy: single modular squaring. The production crypto core is a Montgomery multiplier with modular exponentiation — orders of magnitude more complex. But it slots into the exact same register interface. The SoC, bus, firmware driver, and test infrastructure don't change. That's the point of building the scaffold first.
Part 2 — The SoC
A PicoRV32 RISC-V CPU wired to RAM, a simulation I/O port, and the accelerator. An address decoder looks at the top 4 bits of each memory address to route bus transactions to the right peripheral. A bus adapter translates the CPU's valid/ready handshake into the accelerator's simple wen/ren interface.
Part 3 — The Firmware
C (or Rust) code cross-compiled for RISC-V. It runs on the PicoRV32 CPU. Its job: load data into the accelerator's registers via MMIO, trigger computation, poll for completion, read the result back. The firmware is the translation layer between CPU software and custom hardware.
Part 4 — Testing
Two levels of testing isolate where bugs could be. Level 1 tests the hardware alone. Level 2 tests the complete path: CPU executing real RISC-V instructions, bus transactions routed through the address decoder, and the accelerator responding over MMIO.
Part 5 — Running It All
One command: make sim. Compiles the firmware with a RISC-V cross-compiler, converts it to hex, compiles all Verilog into a simulator executable, runs the simulation, and checks for PASS/FAIL.
